# 버그 진단

어려운 버그를 다루는 규율이다. 단계를 건너뛸 때는 이유를 분명히 밝힌다.

코드를 살필 때는 먼저 `CLAUDE.md` 와 해당 영역 문서를 읽고 모듈 구조를 머리에 넣는다.
- 캐싱·ISR·"페이지가 dynamic 으로 강등됨" → `docs/ARCHITECTURE.md` §3 (특히 §3.3 P-27)
- DB·RLS·권한 → `docs/DB_SCHEMA.md`, `docs/sql/`
- 매거진 지면 → `docs/MHJ_MAGAZINE_DESIGN_BIBLE.md`
- 로컬 실행·포트·워크트리 함정 → `.claude/skills/verify/SKILL.md`

## 가리기 (Redact)

이 스킬은 명령·출력·캡처를 보여주게 한다. **시크릿은 먼저 전부 가린다.** 그 자리에 `<REDACTED>` 를 쓴다.
MHJ 에서 특히 조심할 것: `.env.local` 값, `REVALIDATION_SECRET`, Supabase `service_role` 키, Resend·Anthropic·Gemini 키, 구독자 이메일, 로그인 쿠키.
루프는 환경변수를 읽도록 만들어서, 키가 화면에 나오지 않고 환경 안에 머물게 한다.
캡처에는 인증 헤더가 따라온다. 신호가 담긴 줄만 인용한다.

가린 출력만으로 진단이 안 되면 그렇다고 말하고 사용자에게 묻는다.

## 1단계: 피드백 루프 만들기

**이것이 이 스킬의 전부다.** 나머지는 기계적인 일이다.
이 버그에서 빨갛게 되는 **촘촘한** 통과/실패 신호가 있으면 원인은 반드시 찾는다. 이분 탐색, 가설 검증, 계측은 모두 그 신호를 소비할 뿐이다.
신호가 없으면 코드를 아무리 들여다봐도 소용없다.

여기에 노력을 몰아서 쓴다. **공격적으로, 창의적으로, 포기하지 말 것.**

### 만드는 방법 (대략 이 순서로)

1. **실패하는 테스트** — 버그에 닿는 이음매(seam: 테스트를 꽂을 수 있는 경계 지점)라면 어디든.
   이 repo 에는 jest·vitest 같은 테스트 러너가 없다. `scripts/qa/test-*.mjs` 형식(`node:assert` + 실패 시 `process.exit(1)`)으로 쓴다.
   본보기: `scripts/qa/test-content-html.mjs`.
2. **curl / HTTP 스크립트** — 돌고 있는 서버에 요청한다.
   포트 3003 은 사용자의 메인 dev 서버라 **죽이지 않는다.** 워크트리에서는 3013/3015(prod)·3014(dev)를 쓴다 (`verify` 스킬).
3. **CLI + 고정 입력** — `scripts/qa/fixtures/` 같은 fixture 를 넣고 출력을 정상 스냅샷과 diff 한다.
4. **헤드리스 브라우저 스크립트** — Playwright(이미 의존성에 있음)로 화면을 몰고 DOM·콘솔·네트워크를 단언한다.
   하이드레이션 에러(#418 등), 콘솔 에러, 클릭 동작은 거의 다 여기에 해당한다.
5. **캡처한 실제 흐름 재생** — 실제 요청·페이로드·이벤트 로그를 파일로 저장해 그 코드 경로만 따로 재생한다.
6. **일회용 하네스** — 시스템의 최소 부분만 띄워(의존성은 가짜로) 함수 호출 한 번으로 버그 경로를 탄다.
7. **무작위 입력 루프** — "가끔 틀린 출력"이면 입력 1,000개를 무작위로 넣어 실패 유형을 찾는다.
8. **이분 탐색 하네스** — 두 상태(커밋·데이터·버전) 사이에서 생긴 버그면 "X 상태로 띄우기 → 검사"를 자동화해 `git bisect run` 으로 돌린다.
9. **차이 비교 루프** — 같은 입력을 옛 버전과 새 버전(또는 설정 두 개)에 넣고 출력을 diff 한다.
10. **사람이 끼는 스크립트(HITL)** — 최후의 수단. 사람이 클릭해야만 하면 `scripts/hitl-loop.template.sh`(이 스킬 폴더 안)를 복사해 **사람을** 스크립트로 몬다. 그래야 루프가 구조를 유지한다.
    MHJ 에서는 관리자(`/mhj-desk`) 로그인이 여기에 해당한다. 로그인은 사용자 몫이다.

라이브 전용 증상이면 이것도 루프 재료가 된다:
- `scripts/qa/live-functional-check.mjs`
- Vercel MCP 의 `get_runtime_errors` → `get_runtime_logs`
- Supabase MCP 의 `execute_sql`(조회만)

올바른 루프를 만들면 버그는 90% 고친 것이다.

### 루프 조이기

루프를 하나의 제품처럼 다룬다. 루프가 _하나_ 생기면 **조인다.**
- 더 빠르게 할 수 있나? (준비 단계 캐시, 무관한 초기화 생략, 범위 좁히기)
- 신호를 더 날카롭게 할 수 있나? ("안 죽었다"가 아니라 그 증상 자체를 단언)
- 더 결정적으로 할 수 있나? (시간 고정, 난수 시드 고정, 파일시스템 격리, 네트워크 고정)

30초짜리 들쭉날쭉한 루프는 없는 것보다 조금 나을 뿐이다. 2초짜리 결정적 루프는 촘촘하다. 디버깅의 초능력이다.

### 재현이 들쭉날쭉한 버그

목표는 깔끔한 재현이 아니라 **재현율을 올리는 것**이다.
트리거를 100번 돌리고, 병렬로 돌리고, 부하를 주고, 타이밍 창을 좁히고, sleep 을 끼워 넣는다.
50% 확률 버그는 디버깅할 수 있다. 1% 는 못 한다. 디버깅 가능해질 때까지 재현율을 올린다.
MHJ 사례: #418 은 매거진 페이지를 수천 번 로드하는 루프로 재현율을 셌다 (수정 전 9/3,998 → 수정 후 0/4,000).

### 정말로 루프를 못 만들 때

멈추고 그렇다고 분명히 말한다. 시도한 것을 나열한다. 그리고 사용자에게 셋 중 하나를 요청한다.
- (a) 버그가 재현되는 환경에 접근할 권한
- (b) 시크릿을 가린 캡처(HAR 파일, 로그 덤프, 타임스탬프가 있는 화면 녹화)
- (c) 프로덕션에 임시 계측을 넣어도 된다는 허락

루프 없이 가설로 넘어가지 **않는다.**

### 완료 기준: 빨갛게 될 수 있는 촘촘한 루프

1단계는 루프가 **촘촘하고** **빨갛게 될 수 있을 때** 끝난다.
**명령 하나**(스크립트 경로, 테스트 실행, curl)를 이름으로 댈 수 있어야 하고, 그 명령을 **이미 한 번 이상 돌려 봤어야** 한다(실행문과 출력을 가려서 보여줄 것). 그 명령은 다음을 모두 만족해야 한다.

- [ ] **빨갛게 될 수 있음**: 실제 버그 코드 경로를 타고 **사용자가 말한 바로 그 증상**을 단언한다. 그래서 이 버그에서 빨갛게, 고치면 초록이 된다. "에러 없이 돈다"는 해당 없음. _이 버그를_ 잡을 수 있어야 한다.
- [ ] **결정적**: 돌릴 때마다 같은 판정 (들쭉날쭉한 버그는 위처럼 높은 재현율로 고정)
- [ ] **빠름**: 분이 아니라 초 단위
- [ ] **에이전트가 혼자 돌릴 수 있음**: 사람이 끼는 건 `scripts/hitl-loop.template.sh` 를 통해서만

이 명령이 생기기 전에 코드를 읽으며 이론을 세우고 있다면 **멈춘다. 곧장 가설로 뛰어드는 것이 바로 이 스킬이 막으려는 실패다.**
빨갛게 될 수 있는 명령이 없으면 2단계도 없다.

> **MHJ 의 교훈 — PR #148 → #149.** 매거진 하이드레이션 #418 을 "루트 레이아웃의 sonner `<Toaster>` 때문"이라고 짐작해 PR #148 로 제거하고 머지했다.
> 원인이 아니었다. 실제 원인은 템플릿 `<style>` 의 `useId` 불일치였고, PR #149 에서 재현율을 세는 루프로 입증한 뒤에야 잡혔다.
> 루프를 먼저 세웠다면 #148 을 적용한 뒤에도 루프가 여전히 빨갛게 남아, 머지 전에 "효과 없음"이 드러났을 것이다.

## 2단계: 재현 + 최소화

루프를 돌린다. 버그가 나타나며 빨갛게 되는 것을 본다.

확인할 것:
- [ ] 루프가 **사용자가** 말한 실패를 만들어 내는가? 근처에서 우연히 나는 다른 실패가 아닌가? 버그가 다르면 수정도 틀린다.
- [ ] 여러 번 돌려도 재현되는가? (들쭉날쭉한 버그는 디버깅할 수 있을 만큼 높은 비율로)
- [ ] 정확한 증상(에러 메시지, 틀린 출력, 느린 시간)을 붙잡아 두었는가? 나중 단계에서 수정이 진짜 그 증상을 고쳤는지 검증하는 데 쓴다.

### 최소화

빨갛게 되면 재현을 **여전히 빨갛게 되는 가장 작은 시나리오**로 줄인다.
입력·호출자·설정·데이터·단계를 **하나씩** 잘라 내고, 자를 때마다 루프를 다시 돌린다. 실패를 떠받치는 것만 남긴다.

왜 하는가: 최소 재현은 3단계의 가설 공간을 줄여 준다(의심할 부품이 적어진다). 그리고 5단계에서 깨끗한 회귀 테스트가 된다.

**남은 요소가 전부 실패를 떠받칠 때** 끝난다. 어느 하나를 빼면 루프가 초록이 되는 상태다.

재현 **과** 최소화를 마치기 전에는 넘어가지 않는다.

## 3단계: 가설 세우기

검증하기 전에 **순위를 매긴 가설 3~5개**를 먼저 만든다. 가설을 하나만 만들면 처음 떠오른 그럴듯한 생각에 닻을 내린다.

가설마다 **반증할 수 있어야** 한다. 그 가설이 내놓는 예측을 적는다.

> 형식: "<X> 가 원인이라면, <Y 를 바꾸면> 버그가 사라지고 / <Z 를 바꾸면> 더 심해진다."

예측을 적을 수 없는 가설은 느낌일 뿐이다. 버리거나 날카롭게 다듬는다.

**검증 전에 순위 목록을 사용자에게 보여준다.** 사용자가 도메인 지식으로 순위를 단번에 바꿀 때가 많다("3번 쪽을 방금 배포했다").
이미 배제한 가설을 알고 있을 때도 많다. 싸고 시간을 크게 아끼는 확인 지점이다.
다만 답을 기다리느라 멈추지 않는다. 사용자가 자리에 없으면 내 순위대로 진행한다.

## 4단계: 계측

탐침 하나하나가 3단계의 특정 예측 하나에 대응해야 한다. **한 번에 변수 하나만 바꾼다.**

도구 우선순위:
1. 환경이 지원하면 **디버거 / REPL 검사**. 중단점 하나가 로그 열 줄보다 낫다.
2. 가설을 가르는 경계에 **겨냥한 로그**.
3. "전부 로그 찍고 grep"은 절대 하지 않는다.

**디버그 로그마다 고유 접두사를 붙인다.** 예: `[DEBUG-a4f2]`. 그러면 마지막 정리가 grep 한 번으로 끝난다. 표시 없는 로그는 살아남고, 표시한 로그는 지워진다.

**성능 갈래.** 성능 저하에는 대개 로그가 맞지 않는다.
먼저 기준 측정치를 세운다(시간 측정 하네스, `performance.now()`, 프로파일러, 쿼리 실행 계획). 그다음 이분 탐색한다. 먼저 재고, 그다음 고친다.
MHJ 에서는 응답 시간(예: 검색 API), 이미지 용량(매거진 원본), 캐시 헤더(`x-vercel-cache`)·ISR 여부가 흔한 기준 측정치다.

## 5단계: 수정 + 회귀 테스트

회귀 테스트는 **수정 전에** 쓴다. 단, **올바른 이음매**가 있을 때만.

올바른 이음매란 테스트가 호출 지점에서 일어나는 **실제 버그 패턴**을 그대로 밟는 곳이다.
쓸 수 있는 이음매가 너무 얕으면 그 자리의 회귀 테스트는 거짓 안심만 준다. 예를 들어 버그는 호출자가 여럿이어야 나는데 호출자 하나짜리 테스트밖에 못 쓰는 경우, 버그를 부른 연쇄를 재현 못 하는 단위 테스트인 경우다.

**올바른 이음매가 없다면, 그것 자체가 발견이다.** 적어 둔다. 코드 구조가 이 버그를 못 박지 못하게 막고 있다는 뜻이다. 다음 단계를 위해 표시해 둔다.

올바른 이음매가 있으면:
1. 최소 재현을 그 이음매의 실패하는 테스트로 바꾼다 (`scripts/qa/test-<주제>.mjs`).
2. 실패하는 것을 본다. 코드나 fixture 를 바꿔서 억지로 빨갛게 만들었다면, 원본 사본과 `diff` 해서 그 변경이 실제로 들어갔는지 확인한 뒤에 믿는다.
3. 수정을 적용한다.
4. 통과하는 것을 본다.
5. 최소화하기 전의 원래 시나리오로 1단계 루프를 다시 돌린다.

PR 마다 돌아야 하는 테스트면 source-guard CI 에 편입할지 사용자에게 묻는다.

**MHJ 제약:** dev 서버가 돌고 있으면 `npm run build` 를 하지 않는다 (CLAUDE.md 규칙 11, `.next` 캐시 오염).
dev 는 Turbopack 고정이다. `--turbopack` 을 빼서 재현하려 하지 않는다.

## 6단계: 정리

끝났다고 말하기 전에 반드시:
- [ ] 원래 재현이 더 이상 재현되지 않는다 (1단계 루프 재실행)
- [ ] 회귀 테스트가 통과한다 (또는 이음매가 없다는 사실이 기록되어 있다)

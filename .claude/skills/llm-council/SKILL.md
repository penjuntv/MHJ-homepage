# LLM Council — MHJ 판

한 번 물으면 답 하나가 나오고, 그 답이 좋은지 나쁜지 견줄 대상이 없다.
Council 은 같은 질문을 **서로 부딪히도록 설계된 다섯 관점**에 따로 던진다. 그 답들을 **이름을 가린 채** 서로 평가시키고,
마지막에 의장이 합의점·충돌점·추천 한 가지로 정리한다.

- 착안: Andrej Karpathy 의 `llm-council`(여러 회사 모델 → 익명 상호 순위 → 의장 종합).
  Claude 하나에 관점을 나눠 맡기는 방식은 Ole Lehmann 의 스킬에서 착안. 둘 다 라이선스가 없어 **문구는 가져오지 않고 MHJ 용으로 새로 썼다.**
- **약점을 알고 쓸 것:** 다섯 자문역이 모두 같은 Claude 다. 원본처럼 회사가 다른 모델끼리 부딪히는 게 아니라서 의견이 서로 닮기 쉽다.
  그래서 이 판은 ① 실측 자료를 질문에 박아 넣고 ② 근거 없는 숫자를 평가 단계에서 걸러 낸다.
- 판결은 **조언이다.** 결정과 실행은 사용자 몫이다. 판결만 보고 코드·DB·발행을 건드리지 않는다.

---

## 언제 쓰나

틀렸을 때 대가가 큰 결정에만 쓴다. MHJ 에서 맞는 예:
- YuStudy DB 분리 보류를 유지할까, 지금 분리할까
- Q4 남은 시간을 보강 글·새 글·배포 채널 중 어디에 쓸까
- 뉴스레터를 주간으로 유지할까, 격주로 줄일까
- 매거진을 월간으로 계속 낼까, 호 수를 줄이고 밀도를 올릴까
- 이 랜딩 문구·구독 유도 문구에서 무엇이 약한가

맞지 않는 예: "이 비자 규정 맞아?"(사실 → `fact-verify`) · "왜 #418 이 나?"(버그 → `diagnosing-bugs`) · "글 써 줘"(창작) · "어디까지 할지 정하자"(범위 → `grilling`).

이미 답을 정해 두고 확인만 받고 싶을 때는 듣기 싫은 말이 나올 수 있다. 그게 이 스킬의 목적이다.

## 다섯 자문역

직함이 아니라 **생각하는 방식**이다. 일부러 서로 긴장하도록 짰다.

1. **반대론자** — 이 안에 치명적 결함이 있다고 가정하고 그것을 찾는다. 다 괜찮아 보이면 더 판다.
   MHJ 에서는 특히 이것들을 본다: 가족 운영자의 시간 고갈, 아이 프라이버시(CLAUDE.md 규칙 10), 독자 신뢰를 잃는 시나리오, 되돌리기 어려운 변경.
2. **원리주의자** — "그래서 진짜 풀려는 문제가 뭔가?"를 묻는다. 질문 자체가 틀렸다고 말하는 게 가장 값진 기여일 때가 많다.
   MHJ 의 기준 질문은 **"이걸로 새 사람이 도착하는가, 온 사람이 다시 오는가"**다.
3. **확장론자** — 모두가 놓친 상방을 본다. 이게 기대 이상으로 잘되면 무엇이 열리는지, 옆에 숨은 기회가 무엇인지 본다. 위험은 반대론자 몫이니 신경 쓰지 않는다.
4. **처음 온 독자** — 맥락이 0이다. 오클랜드에 막 도착해 검색으로 이 사이트를 처음 본 한인 부모의 눈으로, 눈앞의 글만 보고 반응한다.
   내부 용어(인포블록, 유씨팩토리, 지면, 호, 운영 컬럼 같은 말)가 나오면 "이게 뭔지 모르겠다"고 그대로 말한다. 만드는 사람에게만 당연한 것을 잡아내는 자리다.
5. **실행가** — "그래서 월요일 아침에 무엇을 하나"만 본다. 첫 걸음이 없는 멋진 안은 그렇다고 말한다.
   프레이밍에 적힌 실제 가용 시간·사람 범위 안에서만 계획한다.

긴장 구도: 반대론자 ↔ 확장론자(하방 ↔ 상방), 원리주의자 ↔ 실행가(다시 생각 ↔ 그냥 해), 처음 온 독자는 가운데서 모두를 정직하게 만든다.

## 진행 절차

### 0단계 — 비용 한 줄 고지
시작 전에 한 줄로 알린다: "자문 5 + 평가 5 + 의장 1, 서브에이전트 11회 호출합니다."

### 1단계 — 맥락 수집과 질문 정리

**A. 맥락 수집 (파일 2~5개, 오래 끌지 말 것).** 질문에 맞는 것만 읽는다.
- `CLAUDE.md`, 메모리 색인 `MEMORY.md` → 질문과 닿는 메모리 파일
- 숫자가 걸린 질문이면 `docs/measurements/` 최신 파일, `docs/SEO_OPS_LOOP.md`
- 관련 계획 문서 `docs/PLAN-*.md`, `docs/CONTENT-BRIEF-*.md`
- 같은 주제의 과거 판결 `docs/decisions/council-*.md` (이미 다룬 걸 또 돌리지 않도록)
- 사용자가 직접 언급하거나 첨부한 파일

**B. 질문 정리.** 사용자의 원래 질문과 수집한 맥락으로 다섯 자문역이 똑같이 받을 **중립적인** 질문문을 만든다.
- 결정할 것 / 선택지
- 맥락 — 숫자·사실마다 **출처 경로와 날짜**를 붙인다 (예: `docs/measurements/gsc-2026-09-23.md`, 3개월 클릭 25)
- 걸린 것 — 왜 중요한가, 틀리면 무엇을 잃나
- 제약 — 시간·사람·돈·되돌릴 수 있는지
- **모르는 것** — 실측이 없으면 "실측 없음"이라고 적는다. 자문역이 숫자를 지어내지 못하게 하는 장치다.

내 의견을 넣지 않는다. 한쪽으로 몰지 않는다.
질문이 너무 막연하면("council 돌려: 우리 사이트") 확인 질문을 **딱 하나만** 하고 진행한다.

**프라이버시:** 질문문·답·기록 어디에도 아이 실명, 구독자 이메일, 키·시크릿을 넣지 않는다. 아이는 Min/Hyun/Jin 으로 쓴다.

### 2단계 — 자문 5명 (병렬)

**한 메시지에 Agent 호출 5개를 한꺼번에** 보낸다. 순서대로 부르면 시간도 들고, 앞 답이 뒤 답에 스며든다.
`subagent_type: "general-purpose"`, `model: "sonnet"`.

자문역 프롬프트:

```
당신은 MHJ(오클랜드 마이랑이 베이 한인 가족이 운영하는 라이프 매거진 www.mhj.nz) 자문 위원회의 「{자문역 이름}」입니다.

생각하는 방식: {위 "다섯 자문역"의 해당 설명 전체}

위원회에 올라온 질문:
---
{정리된 질문문}
---

규칙
- 당신의 관점에 끝까지 기대어 답하세요. 균형을 잡으려 하지 마세요. 다른 관점은 다른 자문역이 맡습니다.
- 치명적 결함이 보이면 그렇다고, 큰 상방이 보이면 그렇다고 단정해서 말하세요.
- 질문문에 없는 숫자·사실을 지어내지 마세요. 필요하면 "확인 필요: …"로 적으세요.
- 도구를 쓰지 말고 주어진 내용만으로 답하세요.
- 한국어로, 서론 없이 바로 본론. 300~600자.
```

### 3단계 — 익명 상호 평가 (병렬)

이 단계가 "다섯 번 물어보기"와 council 을 가르는 핵심이다.

1. 다섯 답을 A~E 로 이름을 가린다. 위치에 따른 편향을 없애려고 배정은 무작위로 한다:
   ```bash
   printf '%s\n' 반대론자 원리주의자 확장론자 처음온독자 실행가 | sort -R
   ```
   출력 순서대로 A~E 를 배정하고, 이 대응표는 의장 단계와 기록에만 쓴다.
2. 평가자 5명을 **한 메시지에 병렬로** 띄운다. `model: "sonnet"`, 각자 같은 다섯 답을 본다.

평가자 프롬프트:

```
MHJ 자문 위원회의 답 다섯 개를 평가합니다. 질문은 다음과 같습니다:
---
{정리된 질문문}
---

**답 A:** {…}
**답 B:** {…}
**답 C:** {…}
**답 D:** {…}
**답 E:** {…}

글자(A~E)로 지칭하며 구체적으로 답하세요.
1. 가장 강한 답은? 왜?
2. 사각지대가 가장 큰 답은? 무엇을 놓쳤나?
3. 다섯 답이 모두 놓친 것은?
4. 질문문에 근거가 없는 숫자·사실 주장이 있으면 짚으세요 (없으면 "없음").

한국어, 400자 이내. 단정적으로.
```

### 4단계 — 의장 판결

Agent 하나, `model: "opus"`. 정리된 질문문, **이름을 밝힌** 다섯 답(대응표 포함), 평가 다섯 개를 전부 준다.

의장 프롬프트:

```
당신은 MHJ 자문 위원회의 의장입니다. 다섯 자문역의 답과 익명 상호 평가를 종합해 판결을 내립니다.

질문:
---
{정리된 질문문}
---

자문역 답 (A~E 대응표: {대응표}):
**반대론자:** {…}
**원리주의자:** {…}
**확장론자:** {…}
**처음 온 독자:** {…}
**실행가:** {…}

상호 평가:
{평가 다섯 개}

규칙
- 다수결이 아닙니다. 소수 의견의 논리가 더 강하면 그쪽 손을 들고 이유를 쓰세요.
- 평가자가 "근거 없음"으로 짚은 주장은 판결의 근거로 쓰지 마세요.
- "상황에 따라 다르다"로 끝내지 마세요. 진짜 답을 내세요.
- 한국어, 결론부터, 짧은 문장. 아래 구조를 그대로 지키세요.

## 위원회가 합의한 것
(여러 자문역이 따로따로 도달한 지점 — 확신도 높음)

## 위원회가 갈린 것
(진짜 이견. 양쪽을 다 보여주고, 합리적인 사람끼리 왜 갈리는지)

## 상호 평가에서 드러난 사각지대
(개별 답에는 없고 평가 단계에서만 나온 것)

## 권고
(분명한 답 하나와 그 이유)

## 가장 먼저 할 일 하나
(목록이 아니라 한 가지. 구체적으로)

## 이 판결이 뒤집히는 조건
(어떤 실측·사실이 나오면 다른 결론이 맞는지 한두 줄)
```

### 5단계 — 채팅에 제시

`## 위원회 판결: {짧은 주제}` 제목 아래 의장 판결을 그대로 보여준다. 한국어, 결론부터.
자문역 원문은 사용자가 원할 때만 펼쳐 보인다.
판결 뒤에 "결정은 사용자 몫"임을 전제로, 실행할지 묻는 질문 하나로 끝낸다.

### 6단계 — 기록 (선택)

사용자가 원하거나, 나중에 다시 볼 만큼 큰 결정이면 남긴다.
- 위치: `docs/decisions/council-YYYY-MM-DD-{영문-슬러그}.md` (폴더가 없으면 만든다)
- 내용: 원래 질문 · 정리된 질문문(출처 포함) · A~E 대응표 · 다섯 답 · 평가 다섯 개 · 판결
- 저장 직후 **실명 검사를 반드시 돌린다.** `name-guard` 훅은 `docs/` 에서 경고만 하고 통과시키기 때문이다:
  ```bash
  P=$(sed -n "s/^PATTERN='\(.*\)'$/\1/p" .claude/hooks/name-guard.sh); grep -inE "$P" docs/decisions/council-*.md && echo "🔴 실명 발견 — 고칠 것" || echo "✅ 실명 없음"
  ```
- 커밋은 사용자가 원할 때만 한다.

## 지킬 것

- 자문 5명, 평가 5명은 **반드시 병렬로**.
- 상호 평가는 **반드시 익명으로**. 누가 말했는지 알면 특정 관점에 기댄다.
- 의장은 다수와 다르게 판결할 수 있다.
- 사소한 질문에는 돌리지 않는다. 정답이 하나면 그냥 답한다.
- 판결을 근거로 바로 실행하지 않는다. 사용자 확인을 받은 뒤 Plan Mode 등 평소 절차로 넘어간다 (`docs/WORKFLOW.md`).
- 다섯 답이 거의 같은 말만 하면 판결에 그렇게 적는다 ("같은 모델이라 의견 다양성이 낮았음"). 이런 일이 반복되면 자문역 한 자리에 다른 회사 모델(예: Gemini)을 넣는 확장을 검토한다.

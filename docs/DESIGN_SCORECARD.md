# MHJ 지면 점수표 — "최상급"을 점수로 정한다

> 근거: `docs/PLAN-homepage-next-2026-11.md` §2(2026-11-09 PeNnY 결재·머지, PR #185) · 같은 문서 §1(MotionSites 스킬에서 아이디어만 빌림 — **스킬은 설치하지 않는다**).
> 쓰는 곳: 페이지별 개편 PR(플랜 4단계 "스펙 → 구현 → 점수"). 설계서 양식과 금지 목록은 `docs/DESIGN_RULES.md` §18.
> 만든 날: 2026-11-09

이 문서는 화면 하나가 "충분히 좋은가"를 두 단계로 판정한다.

1. **기계 탈락 검사** — 하나라도 걸리면 점수를 매기지 않고 탈락이다.
2. **사람 눈 10항목** — 스크린샷을 보고 1~10점을 매긴다. 통과선을 못 넘으면 약한 3곳을 숫자로 고치고 다시 찍는다.

---

## 1. 스크린샷 기준

| 화면 | 폭 × 높이 | 테마 |
|---|---|---|
| 데스크톱 | 1440 × 900 | 라이트 · 다크 |
| 태블릿 | 768 × 1024 | 라이트 · 다크 |
| 모바일 | 390 × 844 | 라이트 · 다크 |

페이지 하나당 **6장**(3화면 × 2테마)에, 같은 수의 **첫 화면** 프레임(0.35초 화면, 그때 아직 안 그려졌으면 첫 그림)이 붙는다. 첫 화면 프레임은 눈으로 깜빡임을 다시 확인하는 데 쓴다.

```bash
# 로컬 운영 빌드(dev 서버가 꺼진 상태에서 빌드 → 3013 에서 next start)
node scripts/qa/live-functional-check.mjs --base=http://localhost:3013 --shots=qa-screenshots/YYYY-MM-DD/local
```

```bash
# 운영 사이트
node scripts/qa/live-functional-check.mjs --shots=qa-screenshots/YYYY-MM-DD/live
```

파일 이름은 `<경로>__<화면>-<테마>.png`(다 그린 뒤) · `…__0350ms.png` 또는 `…__first-<ms>ms.png`(첫 화면)다. 같은 폴더에 `results.json` 이 함께 남는다.

## 2. 기계 탈락 검사 — 하나라도 걸리면 탈락

| # | 항목 | 기준 | 재는 도구 |
|---|---|---|---|
| M1 | 페이지 JS 오류 | 0 | `live-functional-check` "오류" |
| M2 | 실패한 요청(4xx·5xx) | 0 | `live-functional-check` "4xx/5xx" |
| M3 | 가로 넘침 | 0px | `live-functional-check` "가로 넘침" |
| M4 | 깨진 이미지 | 0 | `live-functional-check` "깨진 이미지" |
| M5 | 글자 대비 4.5:1 미만 | 0 | `scripts/qa/audit-contrast.mjs` |
| M6 | axe 접근성 위반 | 0 | `scripts/qa/audit-a11y.mjs` |
| M7 | 제목 글꼴 대체(폴백) | 0 | `live-functional-check` "제목 글꼴 대체" |
| M8 | 흰 화면 깜빡임 | 0 | `live-functional-check` "첫 화면 깜빡임" |
| M9 | 실명 노출 | 0 | `scripts/audit-name-exposure.mjs` · 메타데이터(OG·alt·title)까지 |
| M10 | 모바일 LCP(가장 큰 요소가 그려지는 시간) | 2.5초 미만 | PageSpeed Insights 모바일 |
| M11 | CLS(화면 밀림 점수) | 0.1 미만 | PageSpeed Insights |

### M7·M8 은 무엇을 어떻게 재나

- **M7 제목 글꼴 대체** — 보이는 `h1`~`h3` 마다 첫 번째 글꼴을 읽는다. 그 글꼴이 `document.fonts` 에 선언돼 있는지, 그리고 그 제목의 글자를 덮는 글꼴 파일이 실제로 받아졌는지(`loaded`)를 본다.
  - 선언이 없으면 "선언 없음"으로 잡는다. 2026-10-17(#148)처럼 Google Fonts 가 통째로 빠진 경우다. 화면은 시스템 글꼴로 그럴듯하게 나와서 눈으로는 3주 동안 아무도 몰랐다.
  - 선언은 있는데 받지 못했으면 "미로드"로 잡는다.
  - 한글만 있는 제목의 Playfair 처럼, 그 글꼴이 덮지 않는 글자뿐이면 다음 글꼴 몫이라 넘어간다.
  - 첫 글꼴이 시스템 글꼴 이름(`ui-sans-serif`·`system-ui`·`serif` 등)이면 내려받는 글꼴이 아니라 넘어간다.
  - `document.fonts.check()` 는 쓰지 않는다. 없는 글꼴에도 `true` 를 돌려주기 때문이다(2026-11-09 실측).
- **M8 흰 화면 깜빡임** — 화면 녹화(CDP screencast)로 브라우저가 실제로 그린 프레임을 시각과 함께 받는다. 판정 프레임은 이렇게 고른다.
  - 0.35초에 새 문서 프레임이 이미 떠 있으면 그 프레임을 쓴다.
  - 아직 한 번도 안 그려졌으면 새 문서의 **첫 그림** 프레임을 쓴다. 운영 사이트는 첫 그림이 보통 0.5~1초라 대개 이쪽이다. 흰 화면 깜빡임은 첫 그림에 나타난다.
  - 6초 안에 한 번도 안 그려지면 **판정 보류**다.
  - 즉시 캡처(`Page.captureScreenshot`)나 `page.screenshot` 은 쓰지 않는다. 로딩 중에는 0.5~2.8초 뒤 화면을 돌려주거나 글꼴을 기다려서, 원하는 시점의 화면이 아니다(2026-11-09 실측).
- 판정 기준은 그 프레임을 **다 그린 뒤 화면과 비교**하는 것이다.
  - 다크 테마에서 밝은 픽셀(휘도 235 초과)이 60% 이상이고, 다 그린 화면보다 40%p 이상 많으면 깜빡임이다.
  - 라이트 테마에서 어두운 픽셀(휘도 40 미만)이 같은 조건이면 깜빡임이다.
  - 다 그린 화면도 같은 밝기면 깜빡임이 아니라 그 화면의 디자인이다. 매거진 리더는 라이트에서도 검은 배경이고, 매거진 호 화면은 다크에서도 크림색 본문이다. 비교를 넣기 전 첫 실행에서는 이 둘이 24건 오탐으로 잡혔다.
  - 테마가 아예 적용되지 않은 화면은 M8 이 아니라 기존 "테마 미적용" 결함으로 잡힌다.
- 판정에 쓴 프레임은 `<경로>__<화면>-<테마>__0350ms.png` 또는 `__first-<ms>ms.png` 로 남는다.
- 검사가 실제로 잡는지 일부러 고장을 내 확인했다(2026-11-09, 운영 사이트).
  - Google Fonts 를 막으면 18화면 모두 M7 로 잡혔다.
  - 다크 클래스를 1.5초 늦게 붙이면(늦게 적용되는 테마) 다크 9화면 중 8화면이 M8 로 잡혔다. 나머지 1화면은 첫 그림이 1.9초라 이미 다크가 붙은 뒤였다. 정상 상태에서는 0이었다.

### M10·M11 은 아직 스크립트 밖이다

PageSpeed Insights 모바일 결과를 PR 에 붙인다. 할당량이 바닥난 날은 브라우저 계측으로 대신하고, 그렇게 했다고 적는다(`docs/audits/2026-09-19-live-verification.md` §2.3 방식).

## 3. 사람 눈 10항목 (1~10점)

1~4절 스크린샷 6장을 모두 보고 매긴다. 한 화면에서만 무너져도 그 항목 점수는 그 화면 기준으로 깎는다.

| # | 항목 | 묻는 것 |
|---|---|---|
| 1 | 3초 첫인상 | 누구의 무엇인지 3초 안에 아는가 |
| 2 | 편집 위계 | 먼저 볼 것 → 다음 볼 것이 하나로 읽히는가 |
| 3 | 글자 | 크기 비율·자간·줄 길이(28~42rem)가 맞는가, 한글이 깨지지 않는가 |
| 4 | 구성·여백 | 정렬 기준이 하나인가, 숨 쉴 여백이 일정한가 |
| 5 | 색·빛 | 강조색이 1개인가, 다크 모드에서도 같은 위계인가 |
| 6 | 사진 다루기 | 가족 사진이 잘 잘렸는가, 글자와 겹치지 않는가 |
| 7 | 읽기 편함 | 본문까지 손이 덜 가는가 |
| 8 | 모바일 | 손가락 하나로 다 되는가 |
| 9 | 문구 | 꼬리표·버튼 말이 사실과 맞는가("Waitlist" 같은 틀린 말 0) |
| 10 | 마감 | 줄 끝·간격·정렬의 작은 어긋남이 없는가 |

### 점수를 매기는 눈금

| 점수 | 뜻 |
|---|---|
| 10 | 고칠 곳을 찾지 못한다. 잘 만든 종이 매거진 옆에 놓아도 밀리지 않는다 |
| 8~9 | 작은 흠이 1~2개 있지만 독자는 알아채지 못한다 |
| 7 | 흠이 보이지만 읽는 데 방해는 없다 |
| 5~6 | 독자가 알아채는 흠이 있다. 위계·정렬·문구 가운데 하나가 흔들린다 |
| 1~4 | 깨졌거나 틀렸다(겹침·잘림·사실과 다른 말·읽을 수 없음) |

점수마다 **근거 한 줄**을 붙인다. 근거는 숫자나 위치로 쓴다(예: "모바일 제목 줄 길이 46자 — 기준 넘음", "다크 1440 에서 카드 사이 간격 24px·32px 섞임").

## 4. 통과선

- **평균 8점 이상**
- **7점 미만인 항목이 하나도 없다**

두 조건을 모두 채워야 통과다. 기계 탈락 검사(2절)가 0이 아니면 점수를 매기지 않는다.

## 5. 못 넘으면 — 약한 3곳을 숫자로 고친다, 최대 3번

1. 점수가 가장 낮은 항목 3개를 고른다. 같은 점수면 독자 눈에 먼저 띄는 쪽(1·2·9번)을 앞에 둔다.
2. 항목마다 **고칠 곳 하나와 바꿀 숫자**를 적는다. "더 세련되게" 같은 말은 고침이 아니다.
   - 좋은 예: "제목 자간 -0.8px → 0.02em", "카드 사이 간격 24px → 32px", "히어로 사진 `object-position` 50% 50% → 50% 30%"
   - 고침도 `docs/DESIGN_RULES.md` 안에서만 한다(반지름 12px 이하 · CSS 변수만 · translateY 금지 · §18 금지 목록).
3. 고친 뒤 1절 기준으로 **다시 찍고, 기계 검사부터 다시** 돌린 다음 10항목을 다시 매긴다.
4. **최대 3번**까지 한다. 3번 뒤에도 통과선 아래면 멈춘다. 남은 약점과 점수를 PR 에 적고 PeNnY 판단을 받는다. 같은 자리를 네 번째로 만지면 대개 구조 문제다(`feedback`: 겉칠 말고 구조 개혁).

## 7. 한계

- **10항목 점수는 Claude 가 스스로 매긴다. 객관적인 측정이 아니다.** 그래서 스크린샷과 점수를 PR 에 함께 붙이고 PeNnY 가 확인한다. 점수가 높다는 것만으로 결재를 대신하지 않는다.
- 기계 검사는 "깨진 것"을 잡을 뿐 "좋은 것"을 보증하지 않는다.
- 첫 화면 프레임은 테스트 브라우저의 새 탭 기준이다. 실제 방문자는 이전 화면을 잠시 붙잡아 두는 브라우저 동작(paint holding) 덕분에 덜 보일 수 있다. 그래도 잡히면 고친다.

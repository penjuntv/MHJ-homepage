## 3. 원인(큰 순서)

1. **Google 글꼴 CSS 92KB가 모든 페이지의 첫 그리기를 막는다.** Noto Sans KR 굵기 4개(400·500·700·900) × 한글 조각 100여 개의 `@font-face` 목록이다. 사이트 CSS(14KB)의 6배다. 굵기 900은 코드에서 약 480곳(`fontWeight: 900`·`font-black` 등), 500은 65곳에서 쓰인다. 굵기를 빼는 것은 디자인 변경이다.
2. **글 상세의 글꼴 17파일 439KB.** Literata 3개(본문, 하나에 84KB — 광학 크기 축 7~72 전체를 받는다), Playfair 5개, Noto 4개, Inter 1개가 한 페이지에 실린다.
3. **매거진 호·서가·허브의 이미지 700KB 안팎.** 매거진 호는 기사 사진 8장을 640px로 바로 받는다. 서가와 허브는 아래쪽 `landing-photos` PNG 3장(합 280KB)을 첫 3초 안에 받는다.
4. **홈의 PageSpeed LCP 5.3초.** PageSpeed 는 LCP 요소를 대표 글 사진이 아니라 작은 카드 사진("Relax, Mum, Relax", `loading="lazy"`)으로 잡았다. 그래서 1.38초 늦게 출발한 것으로 계산됐다. 브라우저 계측에서는 3회 모두 대표 글 사진이 LCP 였다. 대표 글 사진에는 `priority`·`fetchPriority="high"`·preload 가 이미 걸려 있다. 왜 이렇게 갈리는지는 아직 모른다 — 고친 뒤 다시 잴 때 확인한다.
5. **/storypress 모바일 CLS 0.076.** 통과선 0.1 아래지만 가깝다.

### 새로 알게 된 것 — 투명도 0 애니메이션이 LCP 를 붙잡는다

글 상세의 첫 사진은 0.83초에 도착해 1.5초 캡처에 이미 보였는데 LCP 는 2.7~2.9초였다. trace 로 보니
첫 사진을 감싼 `.animate-fade-in`(0.8초, 투명도 0→1) 때문이었다. **Chrome 은 투명도 0 으로 그려진 요소를 LCP 로 치지 않고,
애니메이션이 끝나도 그 영역이 다시 그려질 때까지 기록을 미룬다** — 여기서는 글꼴 도착 후 재배치 시점이었다.
그래서 §3 의 "글 상세 글꼴 439KB" 는 LCP 원인이 아니었다(Literata 광학 크기를 18 로 고정해 134 → 62KB 로 줄여도 LCP 그대로).
시작 투명도를 0.01 로 바꾸면 눈으로는 같고 LCP 는 사진이 보이는 시점으로 돌아온다. **키프레임 시작 투명도를 0 으로 되돌리지 말 것**(`tailwind.config.ts` 주석).
§3-4 의 "홈 PageSpeed LCP 가 lazy 작은 카드로 잡힌 이유" 도 같은 래퍼 탓일 가능성이 크다 — PageSpeed 로 다시 확인하면 닫는다.

### 왜 브라우저 계측(1.0~1.9초)과 이렇게 다른가

PageSpeed 모바일은 실제로 느린 망에서 재는 게 아니라, 빠른 망에서 한 번 불러온 기록으로 **느린 4G 를 계산**한다(Lantern).
사진 LCP 는 "사진이 그려진 순간까지 시작된 요청 전부"를 느린 망으로 다시 계산한다. 실제 기록의 LCP 내역은 0.5~1.3초로 짧다.
그런데 첫 그리기는 Google 글꼴 CSS(다른 서버, 렌더링 차단)가 도착해야 일어나고, 그 CSS 가 도착하는 순간 글꼴 파일들이 한꺼번에 출발한다.
그래서 계산에는 글꼴 파일이 전부 "사진 앞"으로 들어간다.

| 페이지 | 받는 Google 글꼴 파일 | PageSpeed 모바일 LCP |
|---|---|---|
| 홈 | 4개 | 3.2초 |
| 사진 글 | 16개 | 6.8초 |

- **정체: 사진이 늦게 그려지는 게 아니라 화면 전체가 약 1초 동안 하얗다.** 실패 회차는 실제 첫 그리기(FCP) 자체가 1.18~1.54초(=LCP). 필름 스트립상 메뉴 줄까지 흰 화면.
  그사이 HTML 해석(DCL)은 0.29초에 끝나 있고 주 스레드는 논다. 통과 회차 FCP 0.18~0.35초.
- **실패 7회는 모두 HTML 문서 도착이 늦은 회차**(0.21~0.79초, PageSpeed 서버 근처 Vercel 캐시가 빈 경우로 보임), 통과 9회는 0.04~0.22초. FCP ≈ 문서 도착 + 약 1.15초.
- **페이지와 무관**: 나타나기 효과(`animate-fade-in`)가 없는 서가도 같은 모양으로 실패(86점, FCP 1.36초). PageSpeed 서버 성능 점수(benchmarkIndex)와도 무관.
- **로컬 재현 안 됨**: 같은 Chrome 157 로 Lighthouse 30회 중 1회(배포 직후 첫 회차), Playwright 로 문서·CSS·글꼴·사진·JS 지연을 흉내 내도 0회.

| 버린 가설 | 근거 |
|---|---|
| 나타나기 효과(투명도 0.01 시작) | 효과 없는 서가도 실패 |
| CSS 가 늦게 와서 | CSS 만 600ms 늦춰도 재현 0/6 |
| 새 배포 직후 정적 파일 캐시 | 배포 1시간 뒤에도 실패, 실패 회차 CSS·사진은 빨랐음 |
| 서버(측정기) 성능 | benchmarkIndex 945 실패 · 722 통과 |

판단: 우리 코드보다 **PageSpeed 측정 환경(문서가 늦게 온 회차에 Chrome 이 첫 화면을 약 1초 보류)** 쪽일 가능성이 크다. 방문자 대부분은 뉴질랜드라 시드니 캐시(HIT, 문서 0.04~0.09초)를 받는다.
확정하려면 실제 방문자 FCP(Vercel Speed Insights)를 봐야 한다 — MCP 권한으로는 못 읽음, 대시보드에서 확인 필요.

### 남은 것
- **실제 방문자 FCP 확인**(Vercel Speed Insights 대시보드, 모바일 p75) — 좋으면 PageSpeed 측정 환경 문제로 종결.
- 갈래 ① 완화 후보: `experimental.inlineCss`(Next 15.5.28 에 있음) — CSS 를 HTML 에 넣어 요청 하나를 없앤다. 대신 모든 페이지 HTML 이 약 14KB(gzip) 커지고 CSS 를 브라우저 캐시로 재사용 못 함. 결재 필요.
- 서가 휴대폰 첫 줄 2칸 미리 받기(§10).

## 13. `experimental.inlineCss` 검토 (2026-11-19, 보류)

같은 커밋(a00c077)을 설정만 바꿔 두 번 빌드해 로컬 운영 서버(3013)에서 비교했다. 운영에는 넣지 않았다.

**HTML 크기** (CSS 57KB 가 `<style>` 과 RSC 데이터에 두 번 들어간다 — Next 문서의 알려진 한계)

| 페이지 | 원본 | gzip | brotli |
|---|---|---|---|
| 홈 | 99→214KB | 16→41KB | 11.8→22.7KB |
| 사진 글 | 105→220KB | 22.5→47KB | 15.0→25.9KB |
| 서가 | 117→231KB | 17.3→41.6KB | 12.7→23.6KB |
| /blog | 143→258KB | 23.4→47.8KB | 16.6→27.5KB |

→ 페이지마다 brotli 약 +11KB, 거의 두 배. 대신 CSS 파일(57KB) 요청 하나가 없어지고, 재방문자도 매번 다시 받는다.

**로컬 Lighthouse(모바일 시뮬레이션, 각 3회, 첫 회차는 사진 캐시 데움이라 제외)**
- 계산상 LCP 는 좋아진다: 홈 2.77→1.67~2.00초 · 사진 글 3.02→1.91~2.59초 · 서가 3.14→1.41~1.55초 · 점수 94~97 → 96~100. "렌더링 차단 요청" 1→0.
- 그러나 **/blog 는 2회 연속 계산상 FCP 3.3초·점수 76.** 실제 관찰값이 문서 도착 0.11~0.13초, DCL 0.13~0.15초, **첫 그리기 1.21~1.22초** — §12 의 "문서 늦음 + 약 1.1초 흰 화면" 과 같은 모양이 inlineCss 빌드에서 로컬로 재현됐다(곧바로 다시 돌린 Lighthouse 6회·Playwright 8회는 0회).

**판단: 보류.**
1. §12 의 흰 화면을 고치지 못한다 — CSS 를 HTML 에 넣은 빌드에서도 그대로 나왔다(§12 의 "CSS 만 600ms 늦춰도 재현 0/6" 과도 맞음). 흰 화면의 원인은 CSS 요청이 아니다.
2. 얻는 것은 PageSpeed 계산 점수 위주다. 방문자 대부분(뉴질랜드)은 시드니 캐시에서 문서·CSS 를 같은 연결로 빨리 받는다.
3. 잃는 것은 실제다 — 모든 페이지 +11KB, 재방문·다음 페이지에서 CSS 캐시 재사용 불가, experimental 기능.
- 다시 볼 조건: 실제 방문자 `vitals`(§ PR #224) 에서 처음 온 모바일 방문의 "FCP − TTFB" 가 크게 나오고 그 차이가 CSS 도착과 맞물릴 때.
- 부수 단서(§12 용): 로컬에서도 문서가 0.1초 넘게 늦은 회차에 1.1초 흰 화면이 났다. 지금까지 Playwright 의 "응답 통째 지연"으로는 0회였으므로, 다음 진단은 **문서를 나눠서 천천히 흘려보내기**(앞부분 먼저, 나머지 늦게)로 재현해 볼 것.

## 14. 1.1초 흰 화면 원인 — Chrome Paint Holding (2026-11-19, 원인 확정 · 고칠 것 없음)

**결론: 우리 코드가 아니다.** HTML 이 `<head>` 안에서 잠깐(0.15초 이상) 멈췄다가 이어서 오면, Lighthouse(휴대폰 화면 흉내) 안의 Chrome 이 첫 그리기를 약 1초 단위로 미룬다. Chrome 의 **Paint Holding**(새 화면이 준비될 때까지 옛 화면을 붙잡아 두는 기능) 때문이다.

**재현 루프** (로컬, 결정적): HTML 만 나눠 보내는 중계 서버(앞 N바이트 → 300ms 쉼 → 나머지) 뒤에서 Lighthouse 모바일을 돌린다.

| 조건 | 결과 |
|---|---|
| /blog, 끊는 곳 300·1000·5000·5400·6000·7250바이트 (`</head>` = 7277) | **실패 12/12** — 첫 그리기 1.30~2.31초(문서 끝 0.31~0.34초) |
| 끊는 곳 7400·9000·16384바이트 (`<body` 시작 뒤) | 통과 6/6 — 문서 끝 직후 그림 |
| **합성 페이지**(CSS·JS·글꼴 없음, 제목 한 줄) head 안에서 300ms 쉼 | **실패 3/3** (1.23~1.33초) |
| 합성 페이지, 쉼 100ms | 통과 2/2 |
| 사진 글(/blog/children-grow-along-the-way) 4096바이트에서 끊기 | 실패 2/2 |
| 페이지 안 Paint Timing 값(방문자 측정 방식)도 같이 기록 | 1.28~1.33초 — Lighthouse 계산 착오가 아니라 실제로 늦게 그림 |

**갈래 가르기** (합성 페이지·실제 /blog 각각):
- `--disable-features=PaintHolding` → 흰 화면 사라짐(합성 3/3, /blog 3/3 통과). `--enable-automation` 도 사라짐.
- Lighthouse 화면 흉내 끔(`--screenEmulation.disabled`) 또는 데스크톱 → 사라짐. 사용자 에이전트·스로틀링·전체 화면 캡처 설정은 무관.
- 백그라운드 억제 끄기 3종·실험 기능(field trial) 끄기 → 그대로. 옛 headless·창 있는 Chrome 에서도 재현(창 있는 쪽 1/2).
- **그동안 Playwright 로 재현이 안 됐던 이유:** Playwright 는 기본 옵션으로 `PaintHolding` 을 꺼 둔다(`playwright-core/.../chromiumSwitches.js`). puppeteer 로 Lighthouse 와 같은 Chrome 옵션·휴대폰 화면을 맞춰도 재현은 안 됐다 — Lighthouse 가 거는 화면 흉내 조합 중 무엇이 방아쇠인지는 미확정.

**PageSpeed 실패와 맞물리는 점:** 실패 7회는 모두 문서 도착이 늦은 회차(§12) — PageSpeed 서버(미국) 근처 Vercel 캐시가 비어 시드니에서 받아 올 때 HTML 앞부분만 먼저 오고 나머지가 한 박자 늦게 오면 정확히 이 모양이다. 운영 캐시 HIT/STALE 응답은 `</head>`·`<body` 가 첫 묶음에 같이 온다(측정: /blog·사진 글·서가 모두 조각 #4 안에 둘 다).

**판단:** 고칠 것 없음. HTML 머리 순서는 Next 가 정하고, 끊기는 곳은 네트워크·캐시가 정한다. PageSpeed 모바일 점수가 회차마다 흔들리는 것은 이것으로 설명된다.
- 실제 방문자(휴대폰 Chrome 도 Paint Holding 은 켜져 있음)에게 생기는지는 `vitals`(PR #224) 로 판정: **"FCP − DCL ≈ 1초 이상"** 이 이 현상의 지문. 1~2주 뒤 p75 분석 때 함께 센다.
- §13 의 inlineCss 빌드에서 로컬 /blog 가 흰 화면이었던 것도 같은 현상(그 회차는 서버 응답이 0.11초 이상 늦었다).

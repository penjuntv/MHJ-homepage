## 0. 결론

- **데스크톱은 9페이지 모두 통과**: LCP 0.65~1.38초, CLS 0.036 이하.
- **모바일은 /storypress 만 통과.** 나머지 8페이지는 LCP 2.6~6.3초.
- **실제 방문자 기록(Chrome 현장 데이터)은 "데이터 없음"**: 방문이 적어서 Google 이 집계하지 않는다. 판정은 실험실 측정으로만 할 수 있다.

## 3. 원인(큰 순서)

1. **Google 글꼴 CSS 92KB가 모든 페이지의 첫 그리기를 막는다.** Noto Sans KR 굵기 4개(400·500·700·900) × 한글 조각 100여 개의 `@font-face` 목록이다. 사이트 CSS(14KB)의 6배다. 굵기 900은 코드에서 약 480곳(`fontWeight: 900`·`font-black` 등), 500은 65곳에서 쓰인다. 굵기를 빼는 것은 디자인 변경이다.
2. **글 상세의 글꼴 17파일 439KB.** Literata 3개(본문, 하나에 84KB — 광학 크기 축 7~72 전체를 받는다), Playfair 5개, Noto 4개, Inter 1개가 한 페이지에 실린다.
3. **매거진 호·서가·허브의 이미지 700KB 안팎.** 매거진 호는 기사 사진 8장을 640px로 바로 받는다. 서가와 허브는 아래쪽 `landing-photos` PNG 3장(합 280KB)을 첫 3초 안에 받는다.
4. **홈의 PageSpeed LCP 5.3초.** PageSpeed 는 LCP 요소를 대표 글 사진이 아니라 작은 카드 사진("Relax, Mum, Relax", `loading="lazy"`)으로 잡았다. 그래서 1.38초 늦게 출발한 것으로 계산됐다. 브라우저 계측에서는 3회 모두 대표 글 사진이 LCP 였다. 대표 글 사진에는 `priority`·`fetchPriority="high"`·preload 가 이미 걸려 있다. 왜 이렇게 갈리는지는 아직 모른다 — 고친 뒤 다시 잴 때 확인한다.
5. **/storypress 모바일 CLS 0.076.** 통과선 0.1 아래지만 가깝다.

### 새로 알게 된 것 — 투명도 0 애니메이션이 LCP 를 붙잡는다

글 상세의 첫 사진은 0.83초에 도착해 1.5초 캡처에 이미 보였는데 LCP 는 2.7~2.9초였다. trace 로 보니
첫 사진을 감싼 `.animate-fade-in`(0.8초, 투명도 0→1) 때문이었다. **Chrome 은 투명도 0 으로 그려진 요소를 LCP 로 치지 않고,
애니메이션이 끝나도 그 영역이 다시 그려질 때까지 기록을 미룬다** — 여기서는 글꼴 도착 후 재배치 시점이었다.
그래서 §3 의 "글 상세 글꼴 439KB" 는 LCP 원인이 아니었다(Literata 광학 크기를 18 로 고정해 134 → 62KB 로 줄여도 LCP 그대로).
시작 투명도를 0.01 로 바꾸면 눈으로는 같고 LCP 는 사진이 보이는 시점으로 돌아온다. **키프레임 시작 투명도를 0 으로 되돌리지 말 것**(`tailwind.config.ts` 주석).
§3-4 의 "홈 PageSpeed LCP 가 lazy 작은 카드로 잡힌 이유" 도 같은 래퍼 탓일 가능성이 크다 — PageSpeed 로 다시 확인하면 닫는다.
